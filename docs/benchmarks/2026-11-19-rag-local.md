# RAG evaluation — local models (2026-11-19)

Real numbers from one run per configuration. Reproduce with `make eval-retrieval` and
`make eval-answers` (per-question details are written to `reports/`, not committed).

## Setup

| Item | Value |
| --- | --- |
| Corpus | 12 synthetic PDFs (2 tenants, 2 superseded versions) → 118 chunks |
| Evaluation set | `data/evaluation/retrieval.yaml`: 47 questions (42 answerable, 5 unanswerable) |
| Embeddings | `qwen3-embedding:0.6b` via Ollama, 1024 dimensions |
| Chat model | `qwen3:8b` via Ollama, temperature 0 |
| Database | PostgreSQL 17 + pgvector 0.8.7 (HNSW, iterative scans), GIN full-text index |
| Hardware | Local NVIDIA RTX 3080 Ti; model already loaded (no cold start in the latencies) |
| Retrieval depth | Top 10 per question for the metrics; top 8 sources for answers |

Categories: factual (16, paraphrased on purpose), exact-code (8), cross-lingual Spanish
(5), outdated-trap (5), point-in-time with `as_of` (4), other-tenant (4), unanswerable (5).
The set was generated from the YAML sources; a script checked that every
labelled section exists in the right document version.

Fusion settings tried offline (same 42 questions): RRF k ∈ {60, 20, 5} × keyword list
length ∈ {20, 10, 5} × keyword weight ∈ {1.0, 0.5}. Best hit@5 0.95 (k = 60, 20, 0.5);
none beat dense alone (0.98).

Reading:
- **forbidden = 0** everywhere: outdated versions and the other tenant never appear,
  because the filters are part of the SQL, not a post-filter.
- Keyword search wins exactly where expected (codes) and loses on paraphrases and
  Spanish. With equal weights, chunks ranked mediocrely by both lists outscored a chunk
  ranked first by one list; PostgreSQL's `ts_rank_cd` has no IDF, so common words make the
  keyword list noisy. BM25 would likely help.
- The factual questions were written to avoid the documents' wording, which favours
  dense retrieval. Differences of one or two questions are within noise for 42 questions.

## Answers (hybrid retrieval, top 8, 3,000-token source budget)

| Check | Qwen3 8B | Qwen3 8B, thinking on |
| --- | --- | --- |
| Answerable questions answered | 41/42 (98%) | 41/42 (98%) |
| Answers citing a relevant section | 40/41 (98%) | 40/41 (98%) |
| Answers containing every reference number | 27/37 (73%) | 32/37 (86%) |
| Answers citing a forbidden version | 0/41 | 0/41 |
| Unanswerable questions refused | 5/5 (100%) | 5/5 (100%) |
| Median latency | 1.0 s | 3.5 s |
| Output tokens (47 questions) | 1,596 | 17,127 |

"Every reference number" is a strict heuristic: it also fails correct answers that leave
out a secondary figure (e.g. the 8-hour resolution next to the 30-minute response) or the
threshold range quoted in the reference. Read the failures, not only the rate.

Errors worth remembering:
- **q06** (is a worn seal covered by the warranty?): retrieval missed "4. Exclusions", and
  the model concluded "yes" from the coverage section. Same with thinking on: no prompt
  or reasoning fixes missing evidence.
- **q38** (who approved USD 75,000 in March 2025?): the right version and table were
  retrieved and cited, and the model still answered "CFO" instead of "Department head".
  Thinking mode answered correctly. Citation validation proves where a claim comes from,
  not that it is right: faithfulness needs a separate judge.
- **q22** (form NSI-FRM-PRC-07): ranked first by keyword search, absent from the dense
  list, and not in the hybrid top 8; the model correctly refused.

## Decisions taken from these numbers

- Hybrid with keyword weight 0.5 is the default; dense is one setting away
  (`RAG_RETRIEVAL_MODE`). Re-run when the embedding model changes (Titan V2).
- No reranker yet (ADR-0007).
- Thinking mode off by default (`LLM_REASONING`): +13 points on reference numbers for
  ~3.5x median latency and ~11x output tokens. Worth it for table-heavy questions; on
  Bedrock the trade-off becomes money, to be measured there.
